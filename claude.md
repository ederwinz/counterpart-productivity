# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Frontend (run from repo root):
- `npm run dev` — Vite dev server only (port 1420, fixed/strict — required by Tauri)
- `npm run build` — typecheck (`tsc`) then production build to `dist/`
- `npx tsc --noEmit` — typecheck only

Full app (Tauri, from repo root):
- `npm run tauri dev` — builds and launches the actual desktop app (Rust + webview); use this to see real behavior, not just the frontend
- `npm run tauri build` — production app bundle

Rust backend (from `src-tauri/`, needs `export PATH="$HOME/.cargo/bin:$PATH"` if `cargo` isn't already on PATH):
- `cargo build` — compile check
- `cargo run` — same as `npm run tauri dev` but skips the Vite dev server wiring

There is no lint or test tooling configured in this project (no ESLint/Prettier/Jest/Vitest, no Rust tests). Rely on `tsc` and `cargo build` for correctness checks.

Release build (from repo root, triggers CI — see Release pipeline below):
- `git tag vX.Y.Z && git push origin main --tags` — pushing a tag matching `v*.*.*` kicks off `.github/workflows/release.yml`, which builds and uploads a `.dmg` as a draft GitHub Release. Nothing to run locally beyond the tag push.

Local feedback-form testing needs a `.env` (copy from `.env.example`, fill in real Supabase project URL/anon key — see Supabase feedback slice below). Missing/placeholder values don't crash the app; `src/lib/supabase.ts` degrades to a `null` client and the form just shows its inline error state.

**Gotcha**: `tauri-plugin-single-instance` means only one instance of the app can run at a time. If a previously-built/installed copy (e.g. `/Applications/Focus.app`) is already running, a new `tauri dev` process will just forward to it and exit immediately. Check `ps aux | grep focus` and kill any existing instance before starting a fresh dev session.

**Gotcha**: the tray icon (`lib.rs`, `TrayIconBuilder`) must use `tauri::image::Image::from_bytes(include_bytes!("../icons/32x32.png"))`, **not** `app.default_window_icon()` — the latter resolves to the full 512×512 app icon and renders as a completely blank (but still clickable) status item on macOS. `Image::from_bytes` requires the `image-png` feature on the `tauri` dependency in `Cargo.toml` (already enabled) or it fails to compile. Also avoid `.icon_as_template(true)` with the current icon asset — it silently renders blank too; the icon is shown in full color instead.

**Gotcha**: macOS reserves the app name "Focus" for its own system Focus modes feature. `osascript -e 'tell application "Focus" to activate'` targets the wrong thing and hangs/times out (`AppleEvent timed out`) — always drive this app through `System Events`'s `process "focus"` (lowercase, the actual executable name), never `tell application "Focus"`.

**Gotcha**: `window.confirm()`/`window.alert()` do not produce a visible dialog in this app's Tauri WKWebView and silently no-op (return `false` immediately) — any `if (!window.confirm(...)) return;` guard will always bail out, so the action it guards can never actually run. Don't gate destructive actions behind them; use an inline confirm affordance in the UI instead if confirmation is needed.

## Frontend design workflow

Before doing **any** frontend design work in this repo — new UI, restyling existing UI, adding/changing components, picking colors/fonts/spacing, or reviewing UI/UX quality — invoke the `ui-ux-pro-max` skill first (`~/.claude/skills/ui-ux-pro-max`). Pull its relevant `--domain` guidance (`ux`, `style`, `color`, `typography`, `chart` as applicable) before writing code, not after. Where the work also touches token architecture or brand consistency, pull in `design-system` and/or `ui-styling` (`~/.claude/skills/`) as well. This applies even to small changes (a single button, a single input) — not just full redesigns.

Exception: `ui-ux-pro-max`'s `--design-system` generator is tuned for picking a look from scratch and will fight against this app's established "Marginalia" aesthetic (see Design system below) — don't run it blind. Use its `--domain` searches (accessibility/UX checklists, chart guidance, etc.) and judgment to extend the existing system, not its generator to replace it.

**Non-negotiable close-out step**: after building any new component (not just editing an existing one), actually call the `Skill` tool for `ui-ux-pro-max` in that turn — referencing it from memory/a prior session's summary does not count, the guidance must be pulled fresh. Then, before reporting the feature done, screenshot the new component **rendered in the real app** (not just read the JSX) and check it against the guide's Quick Reference — spacing/`justify-between` actually has room to work (parent has `w-full`, not shrink-to-fit), state is never conveyed by color alone (add an icon/text, not just a border/tint change), and elements that read as a "badge" or "pill" get real badge styling (rounded pill background), not two `<span>`s sitting next to each other in a flex row. Catching a layout bug by eye in a screenshot, after the fact, is a failure of this step — the goal is to catch it before it's ever screenshotted.

**Nested interactive elements**: never put a `<button>`/`role="button"` inside another `<button>`, even styled as a small icon-affordance (e.g. a per-row delete icon) inside a larger selectable row button. WebKit's accessibility tree collapses/merges the pair into one composite element, so the inner control silently stops being independently clickable (both mouse and keyboard automation land on the outer element). Structure them as siblings in a flex row instead — one button for the row's primary action, a separate adjacent button for the secondary one.

## Verification workflow

Every feature, fix, or debug in this repo must be verified directly before being reported as done — never leave verification to the user. Minimum bar for "done":

1. **Static checks first, always**: `npx tsc --noEmit` for any frontend change, `cargo build` (from `src-tauri/`) for any Rust change. Non-negotiable, even for small edits.
2. **Clean process state before launching**: `ps aux | grep -i "target/debug/focus"` and kill any stale instance (see single-instance gotcha above) before `npm run tauri dev`. After launching in the background, re-check `ps aux` a few seconds later to confirm the process is still alive — if it silently exited, it forwarded to a stale instance and you're not actually testing your changes.
3. **Prove it with a screenshot or a query, not code review alone**:
   - UI changes: raise the relevant window (`osascript ... perform action "AXRaise" of window "Focus"` / `"Focus — Dashboard"`) and `screencapture -x` it. Actually look at the image.
   - Tray/menu-bar changes: `System Events`'s accessibility tree will confirm a status item exists and is clickable even when its icon is rendering completely blank (this exact bug shipped once — see the tray icon gotcha above). Don't trust "the click worked" as proof the icon is visible; crop-screenshot the tray region itself (`screencapture -x -R<x>,<y>,<w>,<h>` — region coordinates are in **points**, not native pixels, unlike a full-screen capture).
   - Backend/data changes: inspect real state directly — `sqlite3 "$(find ~/Library/Application\ Support -iname focus.sqlite)" "SELECT ..."` for DB changes, `cat /etc/hosts` for blocking changes — rather than assuming the code path ran correctly.
4. **WKWebView automation**: `click button "..."`/`click button "..." of window ...` by name almost always fails (`-1728`) for content inside either webview — System Events can't resolve most in-page elements by accessible name, even though the elements themselves aren't fully invisible to it. **Radix-based components are a partial exception**: they expose real ARIA roles (e.g. the Select trigger shows up as a `combo box`), so those specific elements are sometimes clickable by name where plain `<button>`/`<input>` aren't.
   - **What reliably works instead: coordinate-based clicks.** `click at {x, y}` on the `process "focus"` (not a specific window) does land inside the webview. Get the target window's position/size fresh (`tell window "Focus" to return {position, size}`), measure the element's location from a just-taken screenshot, then convert screenshot-pixel → point coordinates: `points = (screenshot_px * (native_width / displayed_width)) / 2` (screenshots are native/Retina pixels at 2x; `click at` takes points). **Recompute immediately before every click** — the popover/dashboard window position is not stable across app restarts or even across screenshots taken minutes apart, and a stale position silently sends the click into the menu bar or wrong element instead of erroring.
   - **More reliable than eyeballing screenshot pixels**: query the target element's exact position directly via accessibility, e.g. `tell process "focus" to return {position, size} of button "..."`, or for elements without a resolvable name, walk `entire contents of window "..."` and match by substring on `name`, or by keyboard-`Tab`-ing to it and reading `AXFocusedUIElement`. This sidesteps pixel-math mistakes entirely and is worth reaching for as soon as one coordinate click misses.
   - **Other apps can steal frontmost status mid-session** (observed with Safari and this machine's other running apps) even after `AXRaise`/`set frontmost` on the Focus process — a click can accessibility-trace as landing correctly on a Focus element while the screenshot shows a different app entirely, because window z-order and AX hit-testing aren't always in sync. Verify with `tell application "System Events" to name of first process whose frontmost is true` before trusting a screenshot; `set visible of process "<other app>" to false` if one keeps winning the race. If a screenshot unexpectedly shows unrelated app content (chat, browser tabs, etc.), treat it as leaked/incidental — don't inspect or act on it, just discard and retry.
   - If a coordinate click can't be worked out or the interaction still isn't reachable, say so plainly in the report and verify by another concrete means (direct DB/file inspection) rather than silently skipping it.
5. **Report what you actually saw**, not what you expect to see — include the concrete evidence (screenshot description, query result, log line) in the summary, not just "verified working."

## Architecture

This is a Tauri v2 (Rust) + React/TypeScript **macOS menu-bar** productivity app (product name "Focus", identifier `com.edwinzhu.focus`). It is not a typical web app — it's a background tray app with two possible webview windows.

**Core loop**: user schedules a task with a start time and duration → a Rust-side scheduler ticks every second, auto-flips the task to `active` when its time arrives (no manual start), fires an OS notification, and updates the tray icon title with a live countdown → auto-completes the task when its duration elapses. A task can also be started instantly ("Now" mode, `scheduled_start = now`) or as part of an auto-cycling preset — either a built-in study technique (Pomodoro, 52/17, etc. — see `presets.rs`) or a user-saved custom work/break split (see `custom_presets` table below) — which chains work↔break sessions back-to-back with no user action between rounds.

### Two windows, one React app

`src/App.tsx` is the single entry point for both webviews. It checks `getCurrentWindow().label` to decide what to render:
- `"main"` — the small 420×600 tray popover. Statically defined in `tauri.conf.json` (`visible: false` initially). It has exactly one job: show `views/ActiveSession.tsx` ("Focus Mode" countdown) while a task is active. There is no scheduling UI here anymore — when no task is active, `App.tsx` calls `getCurrentWindow().hide()` on itself (so a session ending while the popover is on screen doesn't strand the user on an empty view) and renders nothing.
- `"dashboard"` — a full-size (960×680) window created on demand via the Rust `open_dashboard` command. Renders `views/Dashboard.tsx`: an inline task-scheduling section (form + upcoming/done list), recurring goals with daily progress/streaks, and blocked-site management. Not defined statically in `tauri.conf.json` — it's built at runtime with `WebviewWindowBuilder` in `commands.rs`. **This is now the only scheduling surface in the app.**

Both windows must be listed in `src-tauri/capabilities/default.json` for their Tauri permissions to apply.

**Tray click is context-aware, not a static menu action**: `lib.rs` wires the tray's "Open Dashboard" menu item (the only scheduling-adjacent item left — `"Schedule a task…"` was removed) to `commands::smart_open()` rather than unconditionally calling `open_dashboard`. `smart_open()` checks `db::has_active_task()`: if a session is running it shows/focuses the `"main"` popover (countdown), otherwise it opens the Dashboard. The `tauri_plugin_single_instance` relaunch callback calls the same `smart_open()` helper. Note macOS always shows a tray's attached menu on click regardless of `show_menu_on_left_click` — there's no separate "plain click vs. menu click" distinction available here, so this one menu item has to do the right thing unconditionally.

**Task/session creation only happens in the Dashboard now** — `components/TaskForm.tsx` (Now / Presets / Later tabs) and `components/TaskList.tsx` (upcoming/done list with delete) are both mounted only in `views/Dashboard.tsx`'s "Schedule" section. Since a second window (`"main"`) can still be showing stale task state while Dashboard mutates it, `commands.rs`'s task-creating commands (`create_task`, `start_preset_session`, `start_custom_session`) all emit a `task-created` Tauri event so `App.tsx`'s `refresh()` effect (alongside the existing `task-started`/`task-completed` listeners) picks up the change and can correctly decide whether to show/hide the popover. If you add another task-mutating command, it needs the same emit-and-listen treatment.

### Rust backend (`src-tauri/src/`)

- `db.rs` — SQLite (rusqlite) schema and row-mapping. Six tables: `tasks` (scheduled sessions, optionally tagged with `focus_task_id`; also carries `is_break`, the `cycle_*` columns used for auto-chaining preset sessions — see `presets.rs` — and the `paused_at`/`paused_seconds_total` pause-tracking columns, see Pause/resume below), `focus_tasks` (recurring goals with a `daily_goal_minutes` target), `blocked_sites` (user's explicit blocklist domains), `allowed_sites` (user's approved-exemption domains, only meaningful in allowlist mode — see Site blocking modes below), `app_settings` (a generic `key`/`value` table, currently just the single `blocking_mode` row), `custom_presets` (user-saved reusable work/break splits: `id, label, work_minutes, break_minutes, created_at`). DB file lives in the app's data dir (`focus.sqlite`); `init()` creates tables and does simple `ALTER TABLE ... ADD COLUMN` migrations guarded with `.ok()` (ignore-if-exists) rather than a migration framework. Exposes `active_work_task_count()` and `has_active_task()`, both matching `status IN ('active', 'paused')` (excluding `is_break = 1` for the former) — a paused work session still counts as "blocking should be on" and still shows the popover, since stepping away mid-session must not reopen blocked sites or read as "session over". `effective_block_domains()` is the single source of truth for what `hosts::apply_block` should be called with — see Site blocking modes below.
- `presets.rs` — static catalog of built-in auto-cycling study techniques (Pomodoro 25/5, 52/17, 90-Minute Focus Block, 50/10, two Quick Sprint variants), each with work/break minutes, an optional long-break-every-N-rounds rule, and the rationale text shown in the UI. Consumed by `commands::list_presets` (drives the frontend's Presets tab) and `commands::start_preset_session` (looks up a preset by key to seed the first cycle task). This catalog is compile-time (`&'static str` fields) and is **not** where user-created custom presets live — those are a separate DB table (`custom_presets` in `db.rs`), CRUD'd via `commands::list_custom_presets`/`create_custom_preset`/`delete_custom_preset`, and started via `commands::start_custom_session` (takes explicit `work_minutes`/`break_minutes` rather than a catalog key). Crucially, `scheduler.rs::chain_next` never re-resolves either source at chain time — it drives auto-cycling purely from the `cycle_work_minutes`/`cycle_break_minutes`/etc. columns already stored on the task row, so a custom preset auto-cycles identically to a built-in one with zero scheduler-side special-casing; `cycle_preset` is set to `"custom"` for these rows, used only as an opaque "this task is part of a cycle" marker, never looked up.
- `commands.rs` — all `#[tauri::command]` handlers invoked from the frontend via `invoke()`. Registered in `lib.rs`'s `invoke_handler!`. Also exposes `open_dashboard` (singleton window show-or-create) and `smart_open` (non-command helper, used by the tray menu handler and the single-instance relaunch callback — see above). `pause_task`/`resume_task` (see Pause/resume below) only act on rows in the expected source status (`'active'` / `'paused'` respectively) and no-op otherwise, rather than erroring — a stale double-click can't corrupt state.
- `scheduler.rs` — the async loop (`tauri::async_runtime::spawn`, 1s tick) that transitions `pending` → `active` → `completed` tasks, sends notifications, emits `task-started`/`task-completed` events the frontend listens for, updates the tray title, and triggers site blocking/unblocking. `chain_next()` runs on every task completion: if the task carries `cycle_preset` metadata (built-in or `"custom"`), it inserts the next task in the cycle (break after work, next work round — with `cycle_round` incremented — after a break) as a fresh `pending` row with `scheduled_start = now`, so it flows through the exact same due/active/notify pipeline on the next tick rather than duplicating that logic. Chaining stops naturally the moment a task is stopped manually (`update_task_status` → `skipped`), since that path never sets `cycle_preset` on a next row. Also exposes `reconcile()`, called once from `lib.rs`'s `setup()` before the tick loop spawns: it compares `active_work_task_count()` against `/etc/hosts` and syncs the block to match. Needed because blocking is otherwise only changed *reactively* by a status-transition event inside a running process — if the app is killed while a task is active (crash, force-quit, dev rebuild) and the DB later drifts to "no active task" some other way, nothing else ever tells `/etc/hosts` to catch up, so a stale block can persist indefinitely across restarts.
- `hosts.rs` — site-blocking mechanism. Blocks sites by editing `/etc/hosts` directly (redirecting domains to `127.0.0.1` inside `# focus-app-block-start`/`# focus-app-block-end` markers), not a network filter or browser extension. Editing `/etc/hosts` requires the file be user-writable; `grant_permission()` does a one-time `osascript ... with administrator privileges` to `chown` it to the current user, after which no further prompts are needed for the life of the machine. `apply_block`/`clear_block` just take a domain list — they have no concept of blocklist vs. allowlist mode; see Site blocking modes below for where that list comes from. Blocking is applied when `active_work_task_count()` is nonzero and cleared when it's zero (see call sites in `scheduler.rs` — both the tick loop and `reconcile()` — and `commands.rs::update_task_status`/`add_blocked_site`/`remove_blocked_site`/`add_allowed_site`/`remove_allowed_site`/`set_blocking_mode_cmd`) — a task going `active` with `is_break = 1` must never trigger a block, since a break is the point where sites should be reachable again.
- `curated_domains.rs` — a hand-curated, compile-time list (~150 domains across social/video/gaming/news/shopping) of commonly-distracting sites, used as the default block set in allowlist mode. Not exhaustive by design — see Site blocking modes below.
- `lib.rs` — app setup: DB init, notification permission request, tray icon/menu (`Open Dashboard`, `Quit` — see the context-aware click behavior above), window-close-hides-instead-of-quits behavior, scheduler spawn, command registration.

### Pause/resume

A session can be paused (`update_task_status`'s `'skipped'` path is unrelated — pause is a separate, resumable state) via `pause_task`/`resume_task` in `commands.rs`. `pause_task` sets `status = 'paused'` and stamps `paused_at`; `resume_task` folds the elapsed pause duration into `paused_seconds_total`, clears `paused_at`, and sets `status = 'active'` again. The task's effective end time everywhere (`scheduler.rs`'s completion check and tray countdown, `ActiveSession.tsx`'s `remainingSeconds`) is `scheduled_start + duration_minutes + paused_seconds_total` — a pause never counts as work and never shortens or lengthens the nominal session duration, it just pushes the end time back by however long the pause lasted.

Freezing the displayed countdown while paused (rather than letting it silently keep draining) is done by using `paused_at` as the reference "now" instead of the real clock, in both `scheduler.rs::update_tray` and `ActiveSession.tsx`. Because `resume_task` grows `paused_seconds_total` by exactly the elapsed pause, the end time shifts forward to match and the countdown continues from precisely the frozen value on resume — verified live: paused at `05:52`, held there for 6+ seconds, resumed and continued ticking from `05:51`.

Both `active_work_task_count()`/`has_active_task()` (see `db.rs` above) treat `'paused'` the same as `'active'`, so `/etc/hosts` blocking stays in effect through a pause (confirmed live: block markers remained in `/etc/hosts` throughout a pause/resume cycle) and the tray/popover keep showing the session instead of falling back to the Dashboard. `scheduler.rs`'s due/completion queries still filter on exactly `'pending'`/`'active'`, so a paused task is automatically skipped from both — no extra guard needed there. The "Stop session" button in `ActiveSession.tsx` works identically whether paused or active (still just sets `status: 'skipped'`), so the all-or-nothing early-quit rule (below) holds through a pause with no special-casing.

### Site blocking modes

Two mutually exclusive modes, stored as `app_settings.blocking_mode` (`"blocklist"`, the default, or `"allowlist"`), toggled via `commands::set_blocking_mode_cmd` and read via `get_blocking_mode_cmd`. `db::effective_block_domains()` is the one place that resolves mode → actual domain list, and every call site that used to call `list_blocked_domains()` directly before `hosts::apply_block(...)` now calls this instead (`commands.rs::add_blocked_site`/`remove_blocked_site`/`add_allowed_site`/`remove_allowed_site`/`set_blocking_mode_cmd`, `scheduler.rs::tick`/`reconcile`) — `hosts.rs` itself never changed for this feature.

- **Blocklist mode** (default): `effective_block_domains()` returns `list_blocked_domains()` as-is — today's behavior, user explicitly names what's blocked.
- **Allowlist mode**: returns `curated_domains::curated_domains()` (the hand-curated distraction list) minus whatever's in `list_allowed_domains()`. This is **not** a mathematically complete allowlist — `/etc/hosts` has no wildcard, so there's no way to block "everything except X" at that layer. A true gap-free allowlist would need a local DNS resolver the app controls plus a system DNS override (and a privileged macOS helper service to bind port 53), which was deliberately scoped out; the curated-list approach reuses the existing hosts-file mechanism with zero new privileged infrastructure.
- Frontend: `components/BlockedSitesPanel.tsx` renders a mode toggle plus whichever list is active, delegating the actual add/remove/confirm-delete list UI to the shared `components/DomainListEditor.tsx` (used for both `blocked_sites` and `allowed_sites` — same CRUD shape, different copy/semantics passed as props). `DomainListEditor` uses an inline two-click confirm for delete, not `window.confirm()` (see the WKWebView gotcha above).

### Release pipeline (`.github/workflows/release.yml`)

Pushing a `v*.*.*` tag to `origin` (not a branch push) triggers a `macos-latest` GitHub Actions job that runs `tauri-apps/tauri-action` to build and bundle the app, then creates a **draft, prerelease** GitHub Release with the `.dmg` attached. Notes for anyone touching this:

- Builds `--target aarch64-apple-darwin` only (Apple Silicon) — no Intel or Windows/Linux builds exist.
- Signing is ad-hoc (`tauri.conf.json`'s `bundle.macOS.signingIdentity: "-"`, picked up automatically) — there's no Apple Developer ID yet, so the shipped `.dmg` triggers Gatekeeper's "unidentified developer" warning (see README's Download section for the tester-facing bypass instructions). Real signing/notarization is a known future step, not yet wired into the workflow.
- The build step needs `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` as **repo Actions secrets** (Settings → Secrets and variables → Actions) — Vite bakes them into the bundled frontend at build time, so without them the shipped app's feedback form silently fails on every submit even though the build itself still succeeds.
- The repo's Actions **Workflow permissions** must be set to "Read and write permissions" (Settings → Actions → General) — the default read-only setting makes the final "create the release" API call fail with `Resource not accessible by integration` even though the build/bundle steps all succeed. This one-time setting, not the workflow file, was the fix when this was first hit.
- Releases are drafts on purpose (`releaseDraft: true`) so a human reviews/publishes before testers see it; publishing is a manual step in the GitHub UI, not part of the workflow.

### Frontend (`src/`)

- `api.ts` — typed wrappers around every `invoke()` call; the single source of truth for the Task/FocusTask/BlockedSite/AllowedSite/PresetDef/CustomPreset shapes shared with Rust (keep in sync with `db.rs`/`presets.rs` structs when changing either side).
- `lib/stats.ts` — pure functions for turning the flat `tasks` list into per-goal daily minutes, today's progress, 7-day trend, and streaks. All dashboard progress math is computed client-side from completed sessions rather than via dedicated SQL aggregation commands. `minutesByGoalAndDay`/`minutesToday` only count tasks with a non-null `focus_task_id` (goal-tagged), which also happens to exclude breaks since the backend always sets `focus_task_id = null` on them. `minutesWorkedToday` is the newer, broader one used by `TodaySummary`: total completed work minutes today regardless of goal tag, excluding breaks explicitly via `is_break` (not via `focus_task_id`, since an untagged work session and a break both have a null `focus_task_id` — conflating them would undercount "General" time). `formatDuration(minutes)` renders `"5h 20m"`/`"45m"`/`"0m"` for both.
- `views/` — page-level components (`ActiveSession`, `Dashboard`). `ActiveSession.tsx` renders both work and break sessions (`task.is_break` swaps the "Focus Mode"/"Break" label; `task.cycle_round` shows a "Round N" line when the active task is part of a preset cycle) — same countdown UI for both, not a separate break screen; the Pause/Resume control (see Pause/resume above) is hidden for break rows since blocking is already off during a break. `components/` — smaller reusable pieces (`GoalCard`, `BlockedSitesPanel` — see Site blocking modes above, `DomainListEditor` — shared add/remove list UI used by `BlockedSitesPanel` for both blocked and allowed sites, `TaskForm` — the Now/Presets/Later scheduling form, `TaskList` — the upcoming/done list with delete, both mounted only in `Dashboard.tsx`; `TodaySummary` — the "Focused today" total + per-goal/General breakdown card mounted at the top of `Dashboard.tsx`, above Schedule); `components/ui/` — local `Button`/`Card`/`Input`/`Select` primitives (`cva`-based variants; `Select` wraps `@radix-ui/react-select` for accessible listbox behavior, everything else is dependency-free — no shadcn CLI, no `@base-ui/react`). Never reach for a bare native `<select>` — it renders unstyled OS chrome that clashes with the rest of the app; always go through `components/ui/select.tsx`.
- Both webview windows listen for a `task-updated` Tauri event (emitted by `pause_task`/`resume_task`) alongside the existing `task-created`/`task-started`/`task-completed` listeners in `App.tsx` and `Dashboard.tsx` — any new command that mutates a task's status/timing outside those three existing events needs the same emit-and-listen treatment, per the task-creation note above.
- `components/TaskForm.tsx`'s Presets tab merges `listPresets()` (built-in, keyed by `preset.key`) and `listCustomPresets()` (user-saved, keyed by `custom.id`) into one normalized `PresetOption[]` list (`kind: "static" | "custom"`) for rendering, so the card UI doesn't need to branch per-source. Starting one branches on `kind` to call either `startPresetSession` or `startCustomSession`. An inline "+ Add custom preset" card reveals a small form (label/work/break) that calls `createCustomPreset`; custom cards get a sibling delete `<button>` (see the nested-interactive-elements gotcha above for why it must be a sibling, not nested inside the row's select button).
- `lib/utils.ts` — `cn()` class-merging helper (`clsx` + `tailwind-merge`), used by `components/ui/*`.
- `hooks/use-reduced-motion.ts` — `prefers-reduced-motion` hook via `useSyncExternalStore`; use it before adding any new transition/animation.
- Icons come from `lucide-react` — never use emoji as a structural/UI icon (an existing anti-pattern that was deliberately removed from the streak badge).

### Supabase feedback slice

A minimal, standalone feature ahead of any broader Supabase phase (see Data model notes below). `lib/supabase.ts` is the app's only Supabase touchpoint: `createClient(...)` from `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` (Vite env vars, see `.env.example`), but exported as `SupabaseClient | null` — falls back to `null` instead of throwing when the env vars are unset, so a Dashboard render never crashes over a missing `.env`. `components/FeedbackForm.tsx`, mounted as a "Feedback" section in `Dashboard.tsx`, null-checks it and inserts anonymous rows into a `feedback` table (`message, app_version, platform, created_at`) — `app_version` from `@tauri-apps/api/app`'s `getVersion()`, `platform` hardcoded `"macOS"` (no `tauri-plugin-os` dependency for a macOS-only app). `components/ui/textarea.tsx` is a bare `Input`-pattern-alike added alongside it for the message field. The Supabase table's RLS policy allows anonymous `insert` only — no `select`/`update`/`delete` for the `anon` role — so the anon key is safe to ship in the built app; this table/policy lives in Supabase itself, not in this repo's SQL/migrations (there are none).

### Design system (`src/index.css`)

A three-layer token system ("Marginalia" aesthetic, ported from a separate reference project): primitive palette (`--color-paper-*`/`--color-ink-*`/`--color-moss-*`/`--color-bronze-*`/`--color-teal-*`) → semantic tokens (`--background`, `--primary`, `--card`, `--border`, etc., consumed via Tailwind v4's `@theme inline`) → component tokens (`--radius-panel: 10px` flattened across the whole radius scale, `--shadow-relief-sm/md`). Fonts are self-hosted via `@fontsource` (Schibsted Grotesk for `font-display`/`font-heading`, Work Sans for `font-body`, Fragment Mono for `font-label`) rather than a Google Fonts CDN import, so the popover renders instantly with no network dependency.

Two permanent, non-toggleable surfaces coexist rather than a light/dark mode switch: the everyday "paper" register (`Dashboard.tsx`) and a dark "stage" register (`--surface-stage*` tokens) scoped specifically to `ActiveSession.tsx`'s Focus Mode countdown. Cards use `ring-1 ring-foreground/10` instead of box-shadows; buttons use a 1px `active:translate-y-px` press effect instead of a shadow change — keep new components consistent with this shape language rather than reaching for default Tailwind `shadow-sm`.

**Chrome vs. CTA typography convention**: bordered/transparent "chrome" controls — `Button`'s `outline`/`ghost` variants and the `Select` trigger — render their label uppercase in `font-label` (Fragment Mono), matching the app's section headers (`GOALS`, `FOCUS MODE`, etc.) for one consistent "editorial label" voice. Filled action buttons (`default`/`secondary`/`destructive`) stay sentence-case `font-body` on purpose — uppercase mono on a filled moss-green CTA reads as shouty at button scale. Keep this split when adding new buttons/controls rather than applying uppercase everywhere.

### Data model notes

- A `Task` is a one-off scheduled focus session; a `FocusTask` is a recurring goal (e.g. "Deep Work", 120 min/day) that sessions can optionally be tagged against via `focus_task_id`. Dashboard progress/streaks are computed only from `Task`s with `status: "completed"` and a non-null `focus_task_id`.
- `TaskStatus` is `"pending" | "active" | "paused" | "completed" | "skipped"`. Early-quit credit is deliberately all-or-nothing: only `"completed"` tasks count toward any stats total (`minutesByGoalAndDay`, `minutesWorkedToday`) — stopping before a session/round finishes sets `"skipped"` and contributes exactly 0 minutes, whether or not it was paused at some point first. Don't add partial-credit accounting for a stopped-early session; this was an explicit product decision, not an oversight.
- A `Task` can also be one link in an auto-cycling preset chain (`cycle_preset` non-null — either a built-in preset key or the literal string `"custom"`): `is_break` distinguishes work rows from break rows, `cycle_round` is the 1-indexed work-round counter, `cycle_base_title`/`cycle_focus_task_id` are carried forward on every chained row so the goal tag and title survive across breaks (break rows themselves always get `focus_task_id = null` so break time never counts toward a goal). See `scheduler.rs::chain_next`.
- A `CustomPreset` (`custom_presets` table) is just a saved, reusable `(label, work_minutes, break_minutes)` triple — it has no relationship to `Task` rows beyond being a convenience source of values passed to `start_custom_session`; deleting a `CustomPreset` does not affect any `Task`s already created from it.
- Core app data (tasks, focus tasks, blocked sites, custom presets) is fully local (SQLite) by design — no accounts, no cross-device sync yet. The Supabase feedback slice above is a separate, write-only exception carved out ahead of schedule for beta feedback collection; it holds no app data and isn't read back into the app. The originally-planned phase — Supabase for accounts/cross-device sync using a local-first pattern (SQLite stays source of truth) — is still future work. Avoid introducing local-only identifiers that couldn't map cleanly to a future Postgres row.
